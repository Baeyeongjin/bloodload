## 1. 스테이지 1-1이 클리어 불가였다 (수정함)

`KILLS_PER_STAGE` 를 20 → 60 으로 올릴 때 **동시 등장 수를 같이 안 봤다.**

```gdscript
var want := clampi(2 + StageDefs.major_stage(stage) / 8, 2, MAX_FOES)
```

`major_stage(1) / 8` 은 정수 나눗셈이라 0 이다. 큰 단계 1~7 내내 `want = 2` 였다.

몹은 화면 밖에서 제 칸까지 걸어온다(`SPAWN_X 660` → 레인 `380`, 280px ÷
`WALK_SPEED 120` = **2.33초**). 동시 n마리면 초당 `n / 2.33` 마리가 **처리량의
물리적 상한**이고, 이건 DPS와 무관하다.

| 동시 몹 | 초당 상한 | 60초 동안 | 60마리 |
|---|---|---|---|
| 2 (수정 전) | 0.86 | **51마리** | ❌ DPS 무한이어도 불가 |
| 4 (수정 후) | 1.79 | 107마리 | ✅ |

시작 DPS(7.0)·1막 평균 HP(13)로는 수정 전 29마리였다. 큰 단계 1~7의 일반 구간
전부가 같은 상태였으므로 **게임이 1-1에서 막혀 있었다.** 5·10번 구간은
`kills_needed` 가 1이라 통과됐다 — 그래서 "가끔 넘어가진다"로 보였을 수 있다.

### 고친 방식 — 식을 한 곳으로 모았다

같은 식이 **세 군데**에 복사돼 있었다: `_refill_lanes` · `_spawn_wave` ·
`_offline_profile`. 하나만 고치면 화면과 오프라인 계산이 조용히 갈린다.

```gdscript
func _wave_size(at_stage: int) -> int:
	return clampi(2 + StageDefs.major_stage(at_stage) / 8, 4, MAX_FOES)
```

하한을 4로 올린 것이지 `KILLS_PER_STAGE` 를 내리지 않은 이유: 60마리는
"1분에 60마리 = 초당 1마리"라는 의도가 분명한 값이고, 하한 2는 20마리 시절의
잔재다. **의도가 있는 쪽을 남기고 잔재를 고친다.**

> `MAX_FOES 5` 에 칸은 6개(좌3+우3)라 왼쪽 마지막 칸은 여전히 안 쓴다.
> `want = 5` 일 때 `right = 3` 이라 오른쪽 3 + 왼쪽 2 로 끝난다. 그대로 뒀다.

## 2. 오프라인이 실시간보다 앞서 나갔다 (수정함)

`_offline_can_clear` 는 `push = 처치수 × 몹HP ÷ DPS` 만 봤다. **레인 수도 걷는
시간도 모델에 없었다.** 걷기는 `WAVE_WALK_SECONDS` 로 한 번만 뺐다.

DPS가 13.5를 넘는 순간(공격력 1회 훈련이면 14.02) 오프라인은 1-1을 "클리어 가능"
으로 판정하고 단계를 올렸다. 실시간에서는 1장 때문에 영원히 못 넘는다.

DESIGN 이 명시한 불변식 위반이다 — *"오프라인도 같은 벽 앞에서 멈춰야 한다.
안 그러면 실시간으로는 못 넘는 구간을 껐다 켜면 넘어가 있다."*

### 고친 방식

`Balance.stage_seconds()` 를 새로 두고 `can_clear_stage` 가 그것을 쓰게 했다.

```gdscript
static func stage_seconds(kills_needed, foe_hp, hero_dps,
		lanes := 0, walk_seconds := 0.0) -> float:
	var push := push_seconds(kills_needed, foe_hp, hero_dps)
	if lanes <= 0 or walk_seconds <= 0.0:
		return push
	return maxf(push, float(kills_needed) * walk_seconds / float(lanes))
```

**둘 중 느린 쪽이 실제 시간이다.** 인자를 선택형으로 둬서 기존 호출부는 안 건드렸다.

보스·중간보스는 한 마리라 걷는 시간이 예산에서 이미 빠져 있으므로 `lanes = 0` 으로
넘겨 처리량 상한을 안 건다. 걷기 시간은 `_lane_walk_seconds()` 가 실제 레인 좌표와
`SPAWN_X` 에서 계산한다 — 상수로 적어 두면 레인을 옮길 때 같이 안 고쳐진다.

### 남긴 검사 (`tests/BalanceTest.gd`)

DPS 무한 + 2칸이면 60초 초과, 4칸이면 통과, DPS가 모자라면 그쪽이 이긴다.
이 검사가 없으면 나중에 `stage_seconds` 가 `push_seconds` 로 되돌아가도 아무도 모른다.

## 3. 보스 타격 프레임이 어긋나 있었다 (수정함)

`IMPACT_FRAME = 3` 은 주석대로 **7프레임 기준**인데, 새로 들어온 `boss_1~5_attack` 은
**9프레임**이다. 타격이 모션의 43%가 아니라 **33% 지점**에서 나가고 있었다.
08-04 인계는 이 함정을 영웅의 8프레임 전환 예정 작업에만 적어 뒀는데
보스는 이미 걸려 있었다.

**프레임 번호를 버리고 비율로 바꿨다.**

```gdscript
const IMPACT_RATIO := 3.0 / 7.0   # Foe.gd — Main.gd 는 이 값을 그대로 쓴다
```

- `Foe._tick_attack` 의 프레임 계산을 지우고 `_attack_anim >= ATTACK_DUR * IMPACT_RATIO` 로
- `Main.gd` 에 두 군데 하드코딩돼 있던 `3.0 / 7.0` 을 같은 상수로
- `_motion_reach()` 가 **실제 프레임 수에서** 번호를 뽑는다 (7→3, 8→3, 9→4)

7프레임 몹은 값이 그대로고 9프레임 보스만 고쳐진다. 그리고 **인계 1순위인 8프레임
통일 작업의 지뢰가 이걸로 사라진다** — 모션을 다시 뽑아도 타격 지점과 사거리 측정이
따라간다.

## 4. 가호(ward)에 등급 성장이 없다 (진단만)

`SkillTest` 는 VFX 6종 추가 뒤 한 번도 안 돌렸는데, **첫 실행에서 터졌다.**

```
Assertion failed: 승급했는데 안 세다: ward_common
```

`SHAPES["ward"]["power"] = 0.0` 이라 `power()` 로는 커먼과 레전더리가 둘 다 0 이다.
테스트가 `power()` 로 비교한 게 잘못이고 — 그 경우를 위한 `rank()` 가 이미 있다 —
거기까지는 **테스트를 고쳤다**(`rank` 사용).

문제는 게임 쪽이다. `_skill_data()` 가 `duration 6.0` · `bonus 0.30` 을 표에서 그대로
복사하고, `cooldown` 은 등급이 아니라 **레벨만** 본다. 즉:

> 레전더리 **불멸의 심장**과 커먼 **피의 결계**는 완전히 같다.
> 스킬 소환 풀의 **25%(형태 4종 중 1종)에 등급 성장이 없다.**

밸런스 조정이 아니라 **빠진 기능**이라 손대지 않았다. 레전더리 가호에 얼마를 줄지는
결정이 필요하다(지속시간을 늘릴지, 배수를 올릴지, 둘 다인지).

같이 나온 중복 하나는 고쳤다: `_combat_damage()` 가 버프 배수를 `1.3` 으로 따로 적어
둬서 `SHAPES["ward"]["bonus"]`(0.30)를 읽는 `dps()` 와 두 값이 됐다. 지금은 값이 우연히
같아 안 터졌을 뿐이다. 시전 순간의 값을 `_summon_bonus` 에 잡아 두고 한 곳에서만 읽는다 —
버프 도중 장비를 바꿔도 안 사라진다.

### 재작성에서 강화한 것

- **도착 검사를 거리 검사와 분리한다.** 예전 검사는 몹을 뒤로 20px 밀어 두고
  "안 맞는다"를 봤는데, 그러면 거리 때문에 안 맞는 건지 도착을 안 해서 안 맞는 건지
  구분이 안 된다. 지금은 **거리는 닿는 자리로 다시 맞춰 두고 도착 여부만** 어긋나게 한다.
- 전진(`advance`) 구간에는 아무도 못 때린다는 검사 추가
- 칸이 서로 안 겹친다는 검사 추가 (좌우 / 앞뒤)
- 사거리를 `frame_reach(..., 3, ...)` 직접 호출이 아니라 **실제 경로**(`_motion_reach`)로
  잰다 — 그래야 3장의 비율 변경을 이 검사가 실제로 지난다
- 보스 전용 attack 검사를 "비어 있지 않다"에서 **"원본 몹 것보다 프레임이 많다"** 로.
  자산이 없으면 원본으로 조용히 떨어지는데 예전 검사는 그걸 통과시켰다
- `seed(20260804)` 고정 — 아래 두 검사가 굴림 결과에 걸려 있었다

### 재작성하면서 드러난 것 — 08-04 장비 코드는 한 번도 안 돌았다

테스트가 96줄에서 죽어 있었으므로 **그 아래 소환·보관함·합성·분해 검사는 전부
작성만 되고 실행된 적이 없다.** 실제로 두 군데가 틀려 있었다.

| 검사 | 무엇이 틀렸나 |
|---|---|
| 합성 조각 | `승급 결과 키의 조각 == 0` 을 단정했다. 승급 결과가 **이미 보관함에 있으면** 병합 분기라 중복분 1이 더 붙고, 애초에 그 키는 10연에서 이미 조각이 붙어 있을 수 있다(실측 `5 → 3`). **재료 쪽 조각만** 세도록 고쳤다 |

## 7. 밸런스 진단 — **고치지 않았다**

사장님 지적 3건이 전부 수치로 확인됐다. 셋의 뿌리가 하나라 따로 고치면 어긋난다.

```
첫날   5-10    일반 0.21s / 중간 0.72s / 보스 3.14s   DPS 490
1주   50-10    일반 1.48s / 중간 5.19s / 보스 22.52s  DPS 3,362
1개월 100-10   일반 1.52s / 중간 5.33s / 보스 23.13s  DPS 57,589
```

### 7-1. 공격력이 너무 강하다

첫날 일반 몹 TTK가 **0.21초** = 초당 4.8마리. 처리량 상한은 초당 1.8마리다.
**영웅이 시간의 90%를 놀고 서 있다.** 공격력을 올려도 화면이 안 바뀌니
훈련이 보상으로 안 느껴진다.

원인: `hero_damage = 4.0 × 공격력Lv` 는 **레벨당 +100%** 다.
`docs/STATS.md` 는 "레벨당 +2%(합연산)"이라고 적혀 있다 — **문서와 코드가 50배 어긋난다.**
STATS 1장의 "합연산은 무한, 곱연산은 유한" 규칙을 공격력이 어기고 있다.

### 7-2. 곡선이 뒤집혀 있다 — 여기가 제일 심각하다

| 구간 | 적 강화 | DPS 성장 | 결과 |
|---|---|---|---|
| 첫날 → 1주 | **×49.2** | ×6.9 | **7배 뒤처짐** |
| 1주 → 1개월 | ×17.6 | ×17.1 | 거의 균형 |

보스 TTK가 3.14 → 22.52초로 **나빠졌다가**, 그 뒤로 22.5 → 23.1초로 멈춘다.
**첫 일주일에만 벽이 몰려 있고 그 뒤로는 성장 체감이 0이다.**
DESIGN 13-1 의 목표("초반 폭발 → 중반 해금 → 후반 누적")와 정반대이고,
하필 D+1~D+7 리텐션 구간이다.

### 7-3. 체력이 너무 낮다

```
영웅 HP = 100 × (1 + 0.02×(체력Lv−1) + 0.12×방어구)
몹 공격 = enemy_power(stage) × 4
```

몹 공격은 `enemy_power` 를 그대로 타서 **지수로** 오르는데 체력 스탯은 **합연산 +2%** 다.

- 50단계: 몹 4마리 × 13.5 ÷ 2.1초 = 초당 25.7 → 기본 HP 100 이면 **3.9초** 생존
- 100단계: `enemy_power 2,922` → 한 대 **11,687**. 체력 Lv600 이어도 HP 1,300 →
  **한 대에 9번 죽는다**

지금 체력을 지탱하는 건 `0.12 × 방어구` 항 하나뿐이고 체력 스탯 자체는 장식이다.

### 7-4. 손대려면 통째로 해야 한다

| 대상 | 지금 | 후보 |
|---|---|---|
| `hero_damage` | `4.0 × Lv` | `4.0 × (1 + 0.02×(Lv−1))` |
| `hero_max_hp` | `+0.02×(Lv−1)` | `+0.06×(Lv−1)` |
| 몹 공격 | `enemy_power × 4` | `enemy_power^0.75 × 4` |

`hero_damage` 를 문서대로 되돌리면 **DPS가 60배 떨어져** TTK 표가 전부 무효가 되고
`BalanceTest` 체크포인트 검사가 다 깨진다. 적 HP 곡선(`enemy_power`)을 같이 다시
잡아야 하는 작업이라, 세 줄만 고치고 끝나지 않는다.

> **다음 작업자에게**: 7장은 `STATS.md` 4장(전체 DPS 공식)과 `DESIGN.md` 8장
> (수치 곡선)을 같이 열고 시작할 것. 코드만 고치면 문서가 또 어긋난다.

## 8. 스킬이 아예 안 나가던 버그 (수정함)

사장님 신고. **원인이 두 개 겹쳐 있었고, 둘 다 있어야 증상이 나온다.**

### 8-1. 영웅이 기본공격 사거리에서 멈춘다

대시 정지 조건이 `_can_hit_foe(target)` 이었다. 기본값 motion 이 `attack` 이라
사거리 **30** 이다. 그런데 격(strike) 스킬은 `heavy` 모션을 쓰고 그건 **24** 다.

대시는 프레임당 `240 / 60 = 4px` 씩 움직이므로, 간격이 31 을 넘는 상태에서 한 걸음에
`(27, 31]` 로 들어와 멈춘다. **25 이하로는 절대 안 내려간다** → 격 스킬은 영원히
사거리 밖이다.

`_front_reach()` 는 주석부터가 "쓰는 근접 모션 중 **가장 짧은 것**"인데(= 24),
정작 대시가 그걸 안 보고 있었다. 거리 계산을 `_foe_gap()` 하나로 모으고
`_in_front_reach()` 를 붙여 대시가 그 기준으로 붙게 했다.

### 8-2. 대상이 없으면 통째로 포기한다

```gdscript
var skill := _next_ready_skill()      # 1순위 하나만
...
if targeting != "self" and target == null:
	return                             # ← 여기서 끝
```

격은 자동 장착 1순위(위력 2.2 > 파 1.4)라 항상 먼저 뽑히는데, 8-1 때문에 대상이
없으니 매 프레임 여기서 빠져나갔다. **발동이 안 되니 쿨다운도 안 돌고**, 그래서
파·진·가호까지 영영 차례가 안 왔다. 스킬이 하나도 안 나간 이유가 이것이다.

`_ready_skills()` 로 준비된 스킬을 우선순위 순으로 전부 받아, **대상이 없으면 다음
스킬을 본다.** `_next_ready_skill()` 은 그 첫 칸을 돌려주는 한 줄로 남겼다(테스트가 쓴다).

### 남긴 검사

- 기본공격만 겨우 닿는 거리에 세워 두고 `_in_front_reach()` 가 **거짓**인지
  (= 거기서 멈추면 안 된다)
- 격이 절대 안 닿는 거리에서 `_tick_skills()` 를 돌려 `_skill_action == "wave_common"`
  인지 (= 다음 스킬로 넘어가는지)

두 검사 다 수정 전 코드에서는 실패한다.

## 10. 남은 부채

### 10-1. `.import` 줄바꿈 — `.gitattributes` 만으로는 안 끝난다

`--import` 를 돌릴 때마다 `.import` **1,772개가 전부 modified** 로 뜬다. 내용은
한 글자도 안 바뀐다. 실측:

| | 줄바꿈 |
|---|---|
| Godot 이 쓰는 작업본 | **LF** (CRLF 0개) |
| 저장소에 커밋된 blob | **CRLF 포함** |

`.gitattributes` 에 `*.import text eol=lf` 를 넣어 뒀지만, **선언만으로는 이미 커밋된
CRLF blob 이 안 바뀐다.** 끝내려면 한 번의 정규화 커밋이 필요하다:

```bash
git add --renormalize .
```

1,772개짜리 커밋이라 별도 판단이 필요해 하지 않았다. 그때까지는 커밋 전에
`git checkout -- "*.import"` 로 털면 된다(내용이 같으므로 안전하다).
